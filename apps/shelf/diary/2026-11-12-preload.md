surfaces: macos
agent: Claude Code (Claude Fable 5.2)
task: preload the first screen's feed at process start

### Rough

- Shelf's first read did not take the preloaded reply. The preload left 2 ms
  after `main` began and its reply was complete before first pixel, yet the
  Discover read fetched again. The runner sent the asks it makes when the
  TypeScript module loads marked as a refresh, and a refresh bypasses a
  preload. Every preload test passed, because their sources are ready at boot.
  Found by launching Shelf and reading its launch line; about two hours. Fixed
  in the runner and the web runtime (LLP 1162.000 D1).
- A preload is not sent under the agent, so `agent.mjs macos state logs` cannot
  show one. The launch line (`EXACT_OBSERVE_LOG=1`) and a signalled trace's
  journal (`agent.mjs trace --pid`) can. A sentence in `docs/reference.md`
  beside `preload` would have saved the search.
- The journal's `fulfil` line for a read a preload answered says `HTTP cache`.
  The `preload discover … Taken` line above it is the only sign of the source.

### Lean in

- The manifest entry is four lines and the app's code did not change: the
  TypeScript `fetch` is the same call, answered from the reply already held.
- The launch line carries the preload's marks beside the launch's own
  (`handed`, `completed`, `committed`), so one line shows whether it helped.

### Needed

- a request sent at process start: provided (`app.json` `preload`)

### Checkpoints

- macOS build and launch: smooth.
- Launch line, two runs on a loaded machine: handed 147 ms and 462 ms after
  process start (4 ms and 14 ms after `main`), complete at 434 ms and 906 ms,
  before the first commit both times. The read asked at module load was
  answered in 1 ms (`wall 0 ms`); without the preload it waited 710 ms to
  1,270 ms for the network.
- The reply reached the screen 490 ms to 690 ms after it was taken: the main
  thread was busy with the launch's native module calls, which is Shelf's cost
  and not the preload's.
